| Metric | Value |
|---|---|
| Events matched (`n`) | **446** |
| Sum of `duration_seconds` | **2663.13 s** (44.4 min) |
| Avg `duration_seconds` | 5.97 s |
| Max `duration_seconds` | 86.44 s |
| Sum `rows_written` | **830,985** |
| Avg `rows_written` per 100-CIK window | 1863.2 |

`silver_apply_completed` (`edgar_warehouse/application/warehouse_orchestrator.py:3223-3229`)
brackets the loop that parses each bronze snapshot and writes typed rows into the canonical
silver DuckDB — the closest real-world analog to "silver transformation (clean/dedupe/merge)
CPU currently running inside an already-paid task" that this research pass could isolate with
a named, timed event.

**Priced at `medium`'s Fargate rate:** 2663.13 s × $0.00001618/s ≈ **$0.043 total over the
7-day sample** (≈ $0.0062/day, ≈ $0.19/month). This is a genuinely small number, which is
exactly what the ticket's own framing predicts ("effectively free CPU inside an already-paid
ECS Fargate task") — but it is **not the full picture**, and not in the direction that would
make it bigger:

- `silver_apply_completed` brackets SEC-specific **parsing** (raw JSON/XML → typed columns)
  plus the DuckDB write, not a pure dedupe/merge step. Only the dedupe/collapse portion is
  what actually moves to Snowflake (parsing stays wherever bronze artifacts are fetched) — so
  $0.043 is an *overstatement* of the DuckDB-side work this migration removes, which only
  strengthens the "savings are negligible" conclusion below, not weakens it.

- This isolates only the parse-and-apply step. It does **not** include
  `merge_candidate_into_canonical`'s full-file `shutil.copy2` + DuckDB merge over the
  canonical silver file (per `silver_protection.py:692-693`, cited in the existing
  `aws-steady-state-cost-and-silver-size-2026-08-14.md` research file) — that step has no
  dedicated timed pipeline event, so it could not be isolated from total task wall-clock time
  in this pass. Given that same file's finding that "every single successful publish...writes
  a fresh full-size copy" (driving ~400+ GB/day of `silverstage/` S3 churn), the merge/publish
  step is plausibly a larger contributor to task duration than the apply step measured here —
  flagged as an open gap, not estimated.
- **Fargate bills for the task's full reserved vCPU/memory for its whole runtime, not
  per-utilized-cycle.** Removing the silver-transform step from the DuckDB path does not
  mechanically reduce AWS spend unless it (a) shortens the task's total wall-clock duration
  enough to matter, or (b) lets a task profile be downsized (e.g. `medium`'s 4096 MB floor,
  which this repo's own comment attributes partly to silver merge, dropping to something
  smaller). Neither was quantified in this pass.

**Conclusion for Direction 2:** the isolable, named piece of DuckDB-side silver-transform
compute costs on the order of **$0.02–0.20/month** at Fargate `medium` rates — i.e., not a
meaningful dollar amount to net against new Snowflake spend, and structurally can't fully
offset it because Fargate's task-reservation billing model doesn't refund unused CPU. The
"savings" argument in the ticket's framing should be read as "this work is already paid for
regardless," not "removing it frees up a comparable dollar amount" — the real trade this
migration makes is new, additive Snowflake spend in exchange for correctness/architecture
benefits, not a wash against reduced AWS spend.

*(Side data point, not the ticket's main ask: `edgartools-prod-gold-refresh`'s own AWS-side
task, `large` profile, 4 `SUCCEEDED` executions in its execution history —
`gold-refresh-stage15-1786285678` 2m42s, `ticket07-profile-gold-refresh-1785757940` 3m41s,
`erdp-migration-gold-refresh-1785146953` 4m14s, `first-gold-refresh-1785109782` 3m57s
(`aws stepfunctions list-executions`). At `large`'s $0.00003236/s, a ~200s run costs ≈$0.0065
— this is the AWS orchestration/export task cost, separate from and much smaller than the
Snowflake warehouse compute that does the actual dynamic-table refresh work measured in §1.)*

## 4. Refresh-cadence sensitivity (TARGET_LAG)

Given §1 and §3 are both empirically blocked, this section builds a **bottom-up model** from
what *is* measured (pricing, billing mechanics, real refresh-mode determinations, the
near-zero-data refresh floor) plus explicit, labeled assumptions where real data doesn't
exist. It is not a substitute for timing one real backfill once data exists (see
"Recommended next step" below) — it is bounded enough to support a rollback-window decision
today, per the ticket's ask.

### 4a. A structural finding that matters more than the TARGET_LAG number itself

`SHOW DYNAMIC TABLES IN SCHEMA EDGARTOOLS_PROD.EDGARTOOLS_SILVER` plus each table's
`refresh_mode`/`refresh_mode_reason` columns show Snowflake has already decided, for real,
which of the 30 tables get cheap **INCREMENTAL** refresh vs. expensive **FULL** (whole-table
rescan every cycle):

```sql
SHOW DYNAMIC TABLES IN SCHEMA EDGARTOOLS_PROD.EDGARTOOLS_SILVER;
SELECT "refresh_mode", COUNT(*) FROM TABLE(RESULT_SCAN(LAST_QUERY_ID())) GROUP BY 1;
-- INCREMENTAL: 24   FULL: 6
```

The 6 `FULL`-mode tables:

| Table | Reason (verbatim, `refresh_mode_reason`) |
|---|---|
| `SEC_COMPANY_FILING` | "This dynamic table contains a complex query. Refresh mode has been automatically set to FULL for more predictable performance..." |
| `SEC_FINANCIAL_DERIVED` | same ("complex query") |
| `SEC_FINANCIAL_FACT` | same ("complex query") |
| `SEC_OWNERSHIP_DERIVATIVE_TXN` | "Change tracking is not supported on dynamic tables with 'FULL' REFRESH_MODE unless the Dynamic Table has FROZEN WHERE constraint specified." |
| `SEC_OWNERSHIP_NON_DERIVATIVE_TXN` | same |
| `SEC_OWNERSHIP_REPORTING_OWNER` | same |

(The 6 tables with joins found via `grep -il join *.sql` in
`infra/snowflake/dbt/edgartools_gold/models/silver/` were `sec_company_filing.sql`,
`sec_financial_fact.sql`, `sec_ownership_non_derivative_txn.sql`,
`sec_ownership_reporting_owner.sql`, `sec_financial_derived.sql`,
`sec_ownership_derivative_txn.sql` — an exact match to Snowflake's own `FULL`-mode list,
confirming the join is what's forcing `FULL` mode, not something else.)

This matters directly for TARGET_LAG choice: **the ownership tables are exactly the largest
tables in the whole silver layer** (CLAUDE.md elsewhere: "5,583 Form 3/4/5" accessions from a
single 20-CIK/heavy-insider batch; at full-universe scale this is very plausibly the single
largest table after `sec_thirteenf_holding`). A `FULL`-mode table re-scans its *entire* landing
table on every refresh, so tightening TARGET_LAG multiplies cost for these 6 tables roughly
linearly with refresh frequency, while the other 24 (`INCREMENTAL`) tables only pay for the
*new rows since the last refresh* — tightening their TARGET_LAG mostly just means paying the
same total work more often in smaller pieces, not multiplying total cost. **A uniform
TARGET_LAG across all 30 tables is not cost-uniform across all 30 tables.**

### 4b. Critical confound: nothing in this account has ever refreshed on a schedule

Before modeling a fixed TARGET_LAG's cost, it's necessary to establish what's actually driving
refreshes today, because it changes what "TARGET_LAG sensitivity" even means right now:

```sql
SELECT refresh_trigger, refresh_action, COUNT(*), MIN(refresh_start_time), MAX(refresh_start_time)
FROM SNOWFLAKE.ACCOUNT_USAGE.DYNAMIC_TABLE_REFRESH_HISTORY
WHERE database_name = 'EDGARTOOLS_PROD'
GROUP BY 1,2 ORDER BY 1,2
```

| refresh_trigger | refresh_action | count | earliest | latest |
|---|---|---|---|---|
| CREATION | INCREMENTAL | 31 | 04:49:53 -07:00 | 04:59:36 -07:00 |
| CREATION | FULL | 20 | 04:59:15 -07:00 | 05:02:06 -07:00 |
| CREATION | NO_DATA | 36 | 04:59:23 -07:00 | 05:02:05 -07:00 |

**Every single refresh in this account's entire history — 87 rows, gold and silver combined —
has `refresh_trigger = 'CREATION'`. Zero rows have `refresh_trigger = 'SCHEDULED'`, ever.** The
latest refresh timestamp of any kind is `05:02:05.644 -07:00`, matching
`WAREHOUSE_METERING_HISTORY`'s last nonzero bucket (ending `06:00 -07:00`) and its complete
silence since. Two compounding reasons, both confirmed live:

1. All 30 silver tables (and all 20 gold tables) are configured `target_lag = 'DOWNSTREAM'`
   (no `target_lag` is set anywhere in `dbt_project.yml` or the model configs — this is
   dbt-snowflake's default, not a deliberate choice). A `DOWNSTREAM`-lag table with **zero
   downstream consumers** (confirmed: gold's `GET_DDL` still reads from `EDGARTOOLS_SOURCE`,
   not `EDGARTOOLS_SILVER` — see headline finding) has no signal to schedule a refresh
   against, so it simply doesn't.
2. Even if it did, there is no upstream write to react to — the headline finding's
   `LOAD_SILVER_LANDING_TASK` gap means nothing has changed in `EDGARTOOLS_SILVER_LANDING`
   since the tables were created.

**Consequence for this section: the TARGET_LAG sensitivity table below is a model of a
hypothetical future configuration, not an extrapolation from anything this account has been
observed to do.** Today, with the live `DOWNSTREAM` setting, the real answer to "what does the
current TARGET_LAG cost" is close to zero, because it never fires — that is not evidence about
what a *fixed* 15-minute/1-hour/6-hour lag (which Ticket 09/10 would have to deliberately
configure, replacing `DOWNSTREAM`) would cost once it has real upstream data to react to on a
clock. §4d models that hypothetical explicitly as an assumption, not a measurement.

### 4c. Billing mechanics used in the model

- Confirmed live: both warehouses run `auto_suspend = 60` (seconds) (`SHOW WAREHOUSES LIKE
  'EDGARTOOLS%'`). Snowflake bills per-second while a warehouse is not suspended; each
  resume-then-idle-then-suspend cycle costs at minimum the active-plus-idle time before the
  60-second auto-suspend fires.
- X-Small = 1 credit/hour (both warehouses are `size: X-Small`, `SHOW WAREHOUSES`).
- Credit price: **$2.00/credit**, Standard Edition, AWS On-Demand, US baseline — not directly
  queryable from Snowflake itself; sourced via web search (2026-08-18) citing "$2.00 per
  credit (effective Aug 7, 2026)" for AWS US East N. Virginia Standard Edition On-Demand, with
  non-US regions carrying a stated 10-50% premium. This account is `AWS_US_WEST_2`; no
  US-region premium was found in the search results, so $2.00/credit is used as the working
  assumption, flagged as unverified for this specific region.
- Model assumption: all 30 silver models share **one** TARGET_LAG value and the same
  warehouse (`EDGARTOOLS_PROD_REFRESH_WH`), so wake/refresh cycles are treated as roughly
  coalesced per warehouse rather than one full 60-second floor per table — consistent with how
  the ticket frames the choice ("a small table across 2-3 plausible TARGET_LAG settings," not
  per-table).

### 4d. Component A — the auto-suspend "floor" cost, ASSUMING a fixed lag were configured

This component only applies once Ticket 09/10 deliberately replaces `DOWNSTREAM` with a fixed
TARGET_LAG *and* landing data is changing at least once per interval (§4b) — it is a model of
that hypothetical, not a measurement of current behavior.

Wake cycles/day = `86400 / (target_lag in seconds)`. Each wake pays at least the 60-second
auto-suspend floor (today's measured refresh time against empty data was 0–1 second per
table, i.e. well under the 60-second floor, so the floor dominates until real data volume
changes that):

| TARGET_LAG | Wake cycles/day | Floor sec/day | Floor credits/day | **Floor $/month** (×30, $2/credit) |
|---|---|---|---|---|
| 15 min | 96 | 5,760 (1.60 hr) | 1.60 | **≈ $96/month** |
| 1 hour | 24 | 1,440 (0.40 hr) | 0.40 | **≈ $24/month** |
| 6 hours | 4 | 240 (0.067 hr) | 0.067 | **≈ $4/month** |

**Order-of-magnitude reference point, not a validation of the model:** the same arithmetic at
a 1-minute cadence (not in the table above) gives 1,440 wakes/day × 60s = 24 credits/day = 168
credits/week — CLAUDE.md's cited real-world figure for the 1-minute manifest-poll on this same
warehouse class was ~67 credits/week, same order of magnitude. This is presented only as a
rough sanity check that the floor arithmetic isn't off by orders of magnitude, **not** as
evidence the underlying wake-trigger assumption is correct — the manifest task is a
fundamentally different, genuinely clock-driven mechanism (a `SCHEDULE`d task gated by
`SYSTEM$STREAM_HAS_DATA`), whereas §4b just showed that a `DOWNSTREAM`-lag dynamic table with
no consumer produces **zero** scheduled wakes in this account's actual history. A fixed
TARGET_LAG's true wake behavior (does Snowflake skip the resume entirely when nothing changed,
the way the manifest task's stream-gate does, or does it still spin up to check) was not
verified live in this session and is the second-largest open unknown in this ticket, after
§4f's FULL-table row-count rate.

### 4f. Component B — data-volume-driven marginal cost (the part genuinely unmeasured)

This is the piece §1/§3 block from being measured directly. Bounding logic, not a measurement:

- **24 INCREMENTAL tables**: cost scales with rows *added since the last refresh*, not total
  table size. Tighter TARGET_LAG mostly redistributes the same total daily/weekly write
  volume into more, smaller refreshes — it does not multiply total data processed the way it
  does for FULL-mode tables. Expect this component to be small relative to 4d's floor unless
  write volume is very high, based on the closest measured analog (§2: 830,985 rows written
  by the DuckDB-side loader in 2663 CPU-seconds on a single Fargate vCPU — Snowflake's
  warehouse compute is a different engine and not directly comparable at the per-row level,
  but is not expected to be *slower* per row for a single-table `QUALIFY ROW_NUMBER()` scan).
- **6 FULL tables** (`SEC_COMPANY_FILING`, `SEC_FINANCIAL_DERIVED`, `SEC_FINANCIAL_FACT`,
  `SEC_OWNERSHIP_DERIVATIVE_TXN`, `SEC_OWNERSHIP_NON_DERIVATIVE_TXN`,
  `SEC_OWNERSHIP_REPORTING_OWNER`): cost scales with the **entire landing table's row count**
  on every single refresh. This is the component that could plausibly make 15-minute
  TARGET_LAG materially more expensive than 4d's floor alone once the ownership tables carry
  real full-universe volume — but with 0 rows currently loaded, this session has no query
  result to time and no defensible $/row rate to report as measured. **This is explicitly the
  one number this research could not produce**, and it's the single biggest unknown standing
  between "the estimate below" and "a number Ticket 10 should fully trust."

### 4g. A second, likely-dominant lever this research surfaced: the manifest task's live 1-minute drift

§1 already flagged that `SNOWFLAKE_RUN_MANIFEST_TASK` is live at `schedule: 1 MINUTE` in this
account (not the 6-hour value the Terraform module and CLAUDE.md both say it should be) as an
independent drift issue. It is not independent of *this* ticket's decision: that task runs on
the **same warehouse** (`EDGARTOOLS_PROD_REFRESH_WH`) the 30 silver tables are configured to
use. Once real data starts flowing through gold *and* silver shares this warehouse, a
1-minute, `SYSTEM$STREAM_HAS_DATA`-gated poll firing every minute plausibly dwarfs whatever
TARGET_LAG Ticket 10 picks for silver — CLAUDE.md's own cited ~67 credits/week for exactly
this mechanism (§4d) is already larger than every row in the 4h table below except the
15-minute case, and that figure predates this migration's added tables sharing the same
warehouse. **Ticket 10 should treat fixing this drift as a prerequisite alongside, not
subordinate to, picking silver's TARGET_LAG** — a correctly-behaving 6-hour manifest poll
plus a tight silver TARGET_LAG could still cost less than the current 1-minute manifest drift
alone.

### 4h. Combined estimate

| TARGET_LAG | Floor (assumed fixed-lag model, §4d) | Volume-driven marginal (unmeasured, §4f) | **Total estimate** |
|---|---|---|---|
| 15 min | ≈ $96/month | Unknown — dominated by the 6 FULL tables' full-table-rescan cost at real volume; could range from a small addition to a multi-hundred-dollar/month addition depending on ownership-table size at full-universe scale | **≥ $96/month, likely materially higher** |
| 1 hour | ≈ $24/month | Same 6 tables, 4× fewer full rescans/day than 15-min | **≥ $24/month, moderately higher** |
| 6 hours | ≈ $4/month | Same 6 tables, 16× fewer full rescans/day than 15-min | **≥ $4/month, smallest addition of the three** |

All three are on top of (a) whatever gold's own existing dynamic-table spend already is
(itself unmeasured live, per §1), (b) the $2/credit assumption's own uncertainty, and (c) the
`SNOWFLAKE_RUN_MANIFEST_TASK` drift in §4g, which is plausibly the largest single lever of all
three combined once real data flows.

### Recommended next steps to firm this up (not performed in this research pass — read-only scope)

Two gaps stand between this model and a number Ticket 10 should fully trust, in priority
order:

1. **Provision `LOAD_SILVER_LANDING_TASK`** (`infra/snowflake/sql/bootstrap/13_silver_landing_ingest.sql`,
   never applied to this account per §1's headline finding) so `EDGARTOOLS_SILVER_LANDING` has
   any live data to refresh against at all — nothing else here is testable without it.
2. Load one realistic batch of ownership data into
   `EDGARTOOLS_SILVER_LANDING.SEC_OWNERSHIP_NON_DERIVATIVE_TXN` (the largest known FULL-mode
   table) once (1) exists, then run one manual `ALTER DYNAMIC TABLE
   EDGARTOOLS_SILVER.SEC_OWNERSHIP_NON_DERIVATIVE_TXN REFRESH` and read its real credits back
   from `DYNAMIC_TABLE_REFRESH_HISTORY`/`QUERY_HISTORY`, and separately configure one table
   with a real fixed TARGET_LAG (not `DOWNSTREAM`) to observe whether it actually produces
   `refresh_trigger = 'SCHEDULED'` rows and at what cost per wake. Together these two real
   data points — a $/row rate for FULL-mode tables and a real fixed-lag wake cost — would
   replace §4d/§4f's bounding logic entirely.
