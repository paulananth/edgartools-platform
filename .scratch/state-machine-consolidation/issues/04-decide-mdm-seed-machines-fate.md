# Decide keep-or-retire for `mdm_seed_universe` and `mdm_seed_from_silver`

Type: grilling
Status: resolved
Blocked by: 01

## Question

Ticket 01 found both standalone MDM Step Functions (`edgartools-prod-mdm-
seed-universe`, `edgartools-prod-mdm-seed-from-silver`) were built solely
to let an ECS task reach MDM's then-AWS-RDS-hosted Postgres from inside
the VPC. That rationale is now stale — MDM Postgres moved to Snowflake's
native Postgres service (HTTPS, not VPC-gated). Neither has ever executed.

They differ in one important way: `mdm_seed_universe`'s underlying
operation is still actively used today, just via an **inline**
`MdmSeedUniverse` state inside `load_history`'s own composed graph — only
this *standalone, independently-parameterized* (`--tracking-status`/
`--limit` override) entry point sits unused. `mdm_seed_from_silver` has
**no** other caller anywhere in the repo — this standalone SFN is the only
orchestrated path to that command at all.

Decide, for each:
1. Keep as a standalone AWS entry point (useful for its
   independent-parameter override case), retire it (delete the state
   machine, keep the CLI command runnable locally/via a generic single-
   workflow wrapper), or fold it into ticket 02's MDM-tail consolidation
   (both are single-stage MDM machines already conceptually adjacent to
   `mdm_run`/`mdm_backfill_relationships`/etc., which that ticket also
   scopes).
2. If retiring `mdm_seed_from_silver` specifically: confirm the underlying
   `mdm seed-from-silver` CLI command doesn't need a Step Functions
   wrapper at all going forward (e.g. can it run as a one-off `ecs run-
   task`/local invocation when actually needed?), since nothing else
   depends on this exact orchestration shape.

## Answer

Fact-check before the grilling round: both machines turned out to be
already generated by the same generic `write_single_workflow_definition`
loop (`deploy-aws-application.sh:4711`, iterating over
`mdm_migrate mdm_check_connectivity mdm_run mdm_backfill_relationships
mdm_sync_graph mdm_verify_graph mdm_counts mdm_seed_universe
mdm_seed_from_silver`) — neither is bespoke code like `bootstrap_batched`
was, which changes the cost calculus: keeping either one costs almost
nothing extra, and retiring either one doesn't reclaim meaningful code.
Put to the user with this fact in hand:

**`mdm_seed_universe`: keep as a standalone deployed entry point.**
It's free to generate (same shared loop), and unlike `bootstrap_batched`
it preserves a real capability nothing else provides — independently
overriding `--tracking-status`/`--limit` outside `load_history`'s fixed
inline `MdmSeedUniverse` invocation (`warehouse_orchestrator.py`/
`deploy-aws-application.sh:2078-2082`). Zero executions reflects "the
override case hasn't been needed yet," not "superseded" — ticket 01
classified this one as genuinely uncertain, not dead, and nothing here
changes that read. **No code changes required** — this ticket confirms
the status quo, it doesn't ask for anything to be built.

**`mdm_seed_from_silver`: retire.** Unlike `mdm_seed_universe`, nothing
else in the repo calls this operation in any form — no inline state in
any composed machine, no `scripts/ops/trigger.sh` mapping (confirmed via
grep: `trigger.sh` has zero references to `seed-from-silver` or
`mdm_seed_from_silver` today, so there's no operator UX to preserve
either). Its original justification (reaching AWS-RDS-hosted MDM Postgres
from inside the VPC) is fully stale — MDM Postgres is Snowflake-native
(HTTPS) now, so there's no VPC-gating problem left for a dedicated
Step Functions wrapper to solve. The `mdm seed-from-silver` CLI command
itself is untouched and stays runnable via a one-off `aws ecs run-task`
or locally if ever needed — this decision retires only the dedicated
orchestration entry point, not the underlying capability.

**Implementation checklist for the `mdm_seed_from_silver` retirement**
(small — this machine was already the "free," generically-generated kind,
not a bespoke function like `bootstrap_batched`):

1. `infra/scripts/deploy-aws-application.sh:4711`: drop
   `mdm_seed_from_silver` from the `for workflow in ...` loop's word list.
2. Same file, lines ~86-88 and 1290/1300: the
   `MDM_SEED_FROM_SILVER_TRACKING_STATUS` env var / usage-string
   references and the `mdm_seed_from_silver)` case-statement branches in
   `workflow_command_expression`/`workflow_cik_command_expression`-style
   functions become dead once the loop no longer generates this workflow
   — remove them (mirrors item 1 of the `bootstrap_batched` checklist:
   don't leave unreferenced case branches behind).
3. `infra/aws-prod-application.json` line 57: remove the
   `"mdm_seed_from_silver"` ARN entry after the live resource is deleted
   (not before — this file should track deployed reality).
4. `docs/data-architecture.md` line 257: drop `seed-from-silver` from the
   "MDM utility workflows" table row's list of exposed workflows (the CLI
   command itself is unaffected and doesn't need a new doc note — it was
   never documented as an AWS-orchestrated entry separately from this
   row).
5. **Rollback-capture step, same precedent as ticket 03**: snapshot the
   live definition before deleting —
   `aws stepfunctions describe-state-machine --state-machine-arn
   arn:aws:states:us-east-1:690839588395:stateMachine:edgartools-prod-mdm-seed-from-silver
   --query definition --output text > /tmp/mdm-seed-from-silver-definition-snapshot.json`.
6. Explicit `aws stepfunctions delete-state-machine` call after the code
   redeploy lands and the snapshot is captured — same as ticket 03, a
   routine `deploy-aws-application.sh` run does not prune machines removed
   from the generator's workflow list, so this is a separate, deliberate
   destructive step requiring its own go-ahead at implementation time.
7. Run the full test suite green before merging.

Both this ticket and [ticket 03](03-decide-bootstrap-batched-deletion.md)
share the same eventual implementation window (both are AWS-destructive
cleanup items gated on an explicit go-ahead, not routine deploy output) —
worth batching into one implementation pass when that's requested, though
this map itself only decides, per the Destination.
