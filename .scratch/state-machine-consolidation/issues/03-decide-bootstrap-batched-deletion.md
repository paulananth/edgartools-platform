# Decide whether to delete `bootstrap_batched`

Type: task
Status: resolved
Blocked by: 01

## Question

Ticket 01 found `bootstrap_batched` (`edgartools-prod-bootstrap-batched`) is
**dead, not dormant** — `load_history`'s own code comment documents that its
sequential-window design was built specifically to fix a real
`silver.duckdb` consistency race inherent to `bootstrap_batched`'s
concurrent-writer architecture (both read/write the same `cik_batches.jsonl`
artifact; `load_history` replaced it, didn't just add features alongside
it). It is not in CLAUDE.md's "When to use what" table, has zero
executions ever, and nothing else in the repo references it.

Decide: delete the state machine (and its ASL generator,
`write_bootstrap_batched_definition`, in
`infra/scripts/deploy-aws-application.sh`) outright, or leave it deployed
as an inert historical artifact a bit longer (e.g. one more release cycle)
before removing it? If deleting, note any rollback-capture step needed
(mirrors this repo's existing state-machine-definition-snapshot-before-
change precedent, e.g. task #21 from the stage0-stage1-consolidation
session).

## Answer

**Delete outright, no waiting period.** A release-cycle grace window exists
to protect against an undiscovered caller surfacing after removal — there
is no such risk here: `bootstrap_batched` has zero executions ever (not
"low usage," genuinely never run), CLAUDE.md's own "When to use what" table
never listed it, and `load_history` supersedes it by design (its own code
comment documents the sequential-window redesign was built specifically to
close a `silver.duckdb` consistency race inherent to `bootstrap_batched`'s
concurrent-writer architecture — this isn't a parallel option, it's the
thing that was replaced). Waiting a cycle would only be deferring a
decision that's already fully determined by evidence gathered in [Confirm
dead vs. dormant state machines](01-confirm-dead-state-machines.md).

**Rollback-capture step** (same precedent as stage0-stage1-consolidation's
task #21, manual snapshot, no new tooling):

```bash
aws stepfunctions describe-state-machine \
  --state-machine-arn arn:aws:states:us-east-1:690839588395:stateMachine:edgartools-prod-bootstrap-batched \
  --query definition --output text > /tmp/bootstrap-batched-definition-snapshot.json
```

**Implementation checklist** (verified live against the current file —
ticket 04's precedent format, an implementing engineer can follow this
directly):

1. `infra/scripts/deploy-aws-application.sh`: delete
   `write_bootstrap_batched_definition()` (lines 1752-1864, immediately
   followed by `write_load_history_definition()` at line 1865 — confirmed
   via function-boundary grep).
2. Same file, lines ~4355-4361: delete the
   `bootstrap_definition_file`/`write_bootstrap_batched_definition`/
   `upsert_state_machine bootstrap_batched`/ARN-file-write block.
3. `infra/aws-prod-application.json` line 39: remove the `"bootstrap_batched"`
   ARN entry (regenerated by the next deploy anyway, but the live registry
   file should not carry a stale entry after the machine is torn down).
4. **Real landmine found while scoping this ticket, not just cosmetic
   cleanup:** `tests/architecture/test_mdm_sync_graph_limit_per_type.py:31`
   uses the literal string `"\nwrite_bootstrap_batched_definition() {"` as
   an `_END_MARKER` to slice out an unrelated function
   (`mdm_workflow_command_expression`) from the deploy script's source for
   sourcing in a subprocess — it does not test `bootstrap_batched` itself.
   Deleting the function without updating this marker breaks
   `_extract_function_source()`'s `text.index(_END_MARKER, start)` with a
   `ValueError` (marker not found), failing this test's collection/run.
   Update `_END_MARKER` to `"\nwrite_load_history_definition() {"` (the
   function that becomes adjacent after deletion).
5. `docs/data-architecture.md` lines 87 and 249: both reference
   `bootstrap_batched` — line 87 lists it as one of several automated
   consumers of `seed-universe` output (update to drop the reference or
   note it as retired), line 249 is a table row mapping the machine name to
   its stage sequence (`seed-universe -> parallel bootstrap-batch`) — delete
   the row.
6. `CLAUDE.md` lines ~915 and ~999 (the "Phased Pipeline" section's
   `edgartools-prod-bootstrap-batched` callouts, describing it as
   "deployed-but-unverified infrastructure... zero executions ever"):
   update both to past tense — the machine no longer exists — rather than
   leaving them describing a now-deleted resource as merely unverified.
7. Actually delete the live AWS resource: the redeploy that drops the state
   machine from the generated definition set does **not** by itself delete
   the already-deployed `edgartools-prod-bootstrap-batched` ARN in AWS
   (`upsert_state_machine` only creates/updates machines it's told to
   generate; it has no prune step for machines removed from the generator
   set). A separate explicit
   `aws stepfunctions delete-state-machine --state-machine-arn ...` is
   required after the rollback snapshot (step 0) and after confirming the
   code-side deploy succeeded — this is the actual destructive action in
   this ticket and needs its own explicit go-ahead at implementation time,
   not bundled silently into a routine `deploy-aws-application.sh` run.
8. Run the full test suite green before merging, per this repo's standing
   convention for any change touching production orchestration.
