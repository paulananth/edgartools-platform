## Question

`mdm_gold`, `ownership_mdm_gold`, `silver_mdm_gold`,
`bronze_seed_silver_gold`, and `residual_holds_graph` each hand-duplicate
the same `MdmExport -> MdmSync -> MdmVerify` tail (most also `->
GoldRefresh`) as their own literal JSON, generated by their own separate
Python heredoc function in `infra/scripts/deploy-aws-application.sh` --
confirmed via `describe-state-machine` on all 5 live in prod, 2026-08-04
(see map.md's Notes for the exact state lists). Each differs only in its
"head" -- the stage(s) that run before the shared tail (e.g.
`ownership_mdm_gold`'s `ParseOwnershipBronze, MdmPersons, MdmIsInsider`
vs `silver_mdm_gold`'s `SeedUniverse, SeedSilverBatches, BatchSilver,
MdmRun, MdmBackfill`).

Decide the consolidation mechanism. At minimum two real options, likely
more once grilled:

1. **Shared code, still-separate deployed machines.** Extract the
   MdmExport/MdmSync/MdmVerify(/GoldRefresh) tail into one Python helper
   function all 5 heredocs call, eliminating the duplicated JSON at the
   source level. Lower risk -- no change to what's actually deployed, no
   change to how anything (operators, EventBridge, other tooling)
   references these ARNs by name. Fixes the maintenance-duplication half
   of the problem (a tail change currently requires 5 synchronized edits)
   but not the "26 machines" count itself.
2. **Fewer actually-deployed machines, parameterized entry point.**
   Collapse the composed-machine family into one machine whose Step
   Functions execution input selects which head stage(s) to run before
   the shared tail. Reduces the deployed count and the operator-facing
   surface, but is a bigger change: anything that currently starts
   `mdm_gold`/`ownership_mdm_gold`/etc. by ARN or name needs to be found
   and updated, and the "which head" selection logic needs its own design
   (a Choice state keyed on execution input, most likely).

Also resolve, once the mechanism is chosen: whether the 8 standalone
single-stage MDM machines (`mdm_run`, `mdm_backfill_relationships`,
`mdm_sync_graph`, `mdm_verify_graph`, `mdm_counts`, `generation_build`,
`mdm_migrate`, `mdm_check_connectivity`) stay as independent operator
tools regardless of which mechanism wins, or get folded into the same
consolidation.

Depends on nothing (can run in parallel with ticket 01), but its answer is
what makes ticket 01's "should this be deleted or kept" verdicts
implementable.
