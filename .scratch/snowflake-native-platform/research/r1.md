# R1: Compute (Snowpark Container Services)

## Question
Can the loader image run as a service or job in a compute pool? Which pool sizes fit about 0.4 GiB per worker for a database-bound load? What replaces Step Functions' ordering, retries and lane budget?

## Answer
**Yes as a job service, if the image runs to completion and exits. Its activity-polling worker does not fit as it stands.** From the documentation, a job service "terminates when your code exits, similar to a stored procedure", and Snowflake does not restart its containers (services are restarted). The loader polls an AWS Step Functions activity, which Snowflake does not provide, so that polling must be replaced, for example by one job per step started from a task.

**Pool sizes.** The 0.4 GiB figure is the operator's; I did not measure it. From the documentation (AWS), CPU_X64_XS is 1 vCPU / 6 GiB, CPU_X64_S 3 / 13, CPU_X64_M 6 / 28, CPU_X64_L 28 / 116. Memory is not the binding limit at 0.4 GiB per worker. Applying the local rule in HOSTED-LOADS (at most four workers per vCPU), by arithmetic only: 4 workers on XS, 12 on S, 24 on M, 112 on L. Whether more workers per vCPU help a database-bound load is a hypothesis; measure it before sizing.

**Replacements.**
- Ordering: tasks with an AFTER clause. From the documentation, "A task runs after all of its predecessor tasks have finished their own runs successfully." Limits: 100 predecessors and 100 children per task, 1,000 tasks per graph. A job-task needs no warehouse (serverless). The Task Graph Object is a Preview Feature; plan on classic CREATE TASK AFTER graphs.
- Retries: TASK_AUTO_RETRY_ATTEMPTS, 0 to 30, default 0, retries the graph, which is coarser than Step Functions' per-step retry. Keep per-step retry in the loader or make each step a task.
- Predecessor failure: the pages read do not state the default for downstream tasks. Medium confidence that they do not run, from the "successfully" wording.
- Lane budget: no documented equivalent of MaxConcurrency. The documentation says concurrency "depends on the size of the compute pool" (MAX_NODES). The budget would stay in load_jobs.py and be applied by how many job services start. Low confidence in a native expression.
- Replicas: REPLICAS runs several instances of one job, each with SNOWFLAKE_JOB_INDEX and SNOWFLAKE_JOBS_COUNT, for splitting a source.
- Waits: run jobs synchronously; the documentation warns an async job lets the task report completion early.
- Timeouts and heartbeats: none documented. Step Functions' per-step timeouts have no documented equivalent.
- Termination: SIGTERM, then a 30-second graceful window.
- Handoff: sessions are not shared between job services; pass data through a stage or table.
