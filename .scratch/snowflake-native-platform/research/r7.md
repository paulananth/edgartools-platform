# R7 Monitoring: what replaces the exporter and Grafana in Snowflake

Question (item 7): what replaces the Prometheus exporter and Grafana dashboards inside Snowflake, and what must the load-monitoring skill keep?

Sources: Snowflake documentation only (URLs at the end). "Documentation" = read on the page. No account touched; nothing measured.

## Mapping

| Today (exporter.py, Grafana) | Snowflake feature | Note |
|---|---|---|
| `load_monitor_up`, snapshot age | OTLP metrics in the event table (`RECORD_TYPE = 'METRIC'`), queried by `TIMESTAMP` | Staleness is a query, not a scrape |
| `load_steps{state}`, `load_step_state`, `load_steps_total` | Metrics, one row per sample; Snowsight Monitoring or a Streamlit page | Keep the six state codes |
| `load_step_attempt/workers/elapsed/bound/log_age/cpu/memory/rows_per_minute` | Metrics labelled by lane and step | Labels stay counts and names |
| `load_step_why`, `load_step_cause` | Log records (`RECORD_TYPE = 'LOG'`), not metric labels | Text belongs in logs |
| `load_lane_budget`, `load_workers_running`, etc. | Metrics; lane board as a Streamlit in Snowflake app | Keep the `limit` label |
| `load_machine_*` | Platform metrics `system`, `system_limits` (`spec.platformMonitor`) | Covers the container only |
| Grafana dashboard | Classic Snowsight dashboards are being retired (removal began 2026-06-22). Use Streamlit in Snowflake, or new Snowflake Dashboards (public preview, `.dash`, each tile a SQL query) | Annotations become query rows |
| Alerts (not built) | New-data alert on the event table; action `SYSTEM$SEND_SNOWFLAKE_NOTIFICATION` | Event table is an allowed source |
| Prometheus scrape | Sidecar scrape for services only, not jobs; compute-pool node endpoint on port 9001 `/metrics`, which we poll ourselves | See below |

## Limits and cost (documented)

- Event table ingest: 1 MB/s per node for logs; 1 MB/s per node combined for metrics and traces; 16 KiB maximum record.
- `SPCS_GET_LOGS` defaults to one day. `SYSTEM$GET_SERVICE_LOGS` returns at most 100 KB; development use.
- Levels: `METRIC_LEVEL` is ALL or NONE; `LOG_LEVEL` captures WARN and above by default; `LOG_EVENT_LEVEL` covers compute-pool events.
- Cost: telemetry is billed per GB sent to an event table ("Telemetry Data Ingest"), in credits. The per-GB rate is in Table 5 of the Service Consumption Table, which I did not reach. Best-supported answer: a credit line per GB, rate unknown here (confidence high on the unit, none on the number).
- Alerts: serverless bills compute-hours; warehouse alerts bill warehouse time, at least one minute for a new-data alert.
- Event table retention is not stated. We write our own retention job.
- Compute-pool hourly credits are not on the pages I read; that belongs to R9.

## Prometheus-compatible export

Best-supported answer (confidence medium-high): no managed Prometheus server. A service can expose Prometheus metrics for a sidecar to scrape; jobs cannot. Prometheus Summary is unsupported (use Histogram). A load runs as a job, so it pushes OTLP metrics to the collector, and the event table is the store.

## What the load-monitoring skill keeps

- Metric names, label set (counts, states, times, no row values), the six state codes and the thresholds in `design.py`.
- Read-only status. Inside Snowflake the status comes from the job's own logs and state, not `ps` on a shared process list. Inference from the skill's text (confidence high), not measured.
- Every panel keeps its interaction description.
