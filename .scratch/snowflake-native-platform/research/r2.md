# R2: Databases (Snowflake Postgres)

## Question

Does Snowflake Postgres satisfy the six PostgreSQL 16 stores (version, extensions, connection limits, roles, no run-time DDL)? Is it reachable from a Snowpark Container Services (SPCS) service with no public internet hop? Does MDM's standard-SQL portability hold?

## Answer

- **Version: yes.** Majors 16, 17 and 18; latest 16 minor is 16.13. From the documentation. GA versus preview: not stated on the pages read.
- **Extensions: the catalog covers the likely set** (pgcrypto, pg_trgm, uuid-ossp, citext, ltree, vector, pg_cron, pgaudit, pg_stat_statements, postgres_fdw). From the documentation. Not checked: which extensions our stores use.
- **Connections: 500 by default** (`max_connections`, restart to change), PgBouncer in transaction mode. From the documentation. Six databases fit the documented limits of 32 databases and 64 roles per instance.
- **Roles: partial.** `snowflake_admin` (not superuser; creates roles and databases) and `application` (non-superuser) are documented. No read-only or least-privilege role is documented. Our CONNECT-only login would be ordinary Postgres GRANT/REVOKE at provisioning (inference). The name `snowflake_write` in our skill is not in the Snowflake pages: not found.
- **No run-time DDL: not enforced by Snowflake.** The docs block superuser logins, `ALTER SYSTEM` and catalog edits, but do not block DDL for `snowflake_admin`. The rule would be a grant made at provisioning. Achievable by standard grants (inference, high confidence); not tested.
- **Reachability: no documented no-hop path (medium-low confidence).** Instances accept no incoming connections by default. Ingress needs a network policy with `POSTGRES_INGRESS` rules (IPv4 only; `0.0.0.0/0` advised against). PrivateLink needs Business Critical or higher; VPC peering is AWS only. SPCS egress uses an external access integration: `HOST_PORT` (public, full hostname) or `PRIVATE_HOST_PORT` (a private endpoint in the customer's cloud account, same cloud and region). No page says a service reaches a Postgres instance over the Snowflake-internal network, or whether compute-pool egress satisfies a `POSTGRES_INGRESS` rule. Best-supported answer: a service reaches the instance through its ingress endpoint. A probe by the owner on a non-production instance is needed before claiming "no hop".
- **Port 5432 is allowed** for SPCS rules (22, 80, 443 and 1024+). From the documentation.
- **Repo fact (read only):** today's hosted MDM is one Snowflake Postgres instance with six databases, reached by a `POSTGRES_INGRESS` policy, so today's path is a policy-controlled route. From `skills/aws-snowflake-operations/SKILL.md`.
- **Latency: not measured.**

## MDM standard-SQL portability

- Snowflake Postgres is PostgreSQL, so the PostgreSQL adapter's SQL should run unchanged. From the documentation (existing tools and ORMs work unchanged); the application to our SQL is inference.
- `scripts/dev/adapter_test.sh` runs the `postgresql` and `mysql` engines only. Not run against Snowflake Postgres: the claim for this target is unproven. Measured: no.
- The repo's rule that each adapter keeps equivalent transaction and guard behaviour still holds. Whether a non-superuser `snowflake_admin` changes the guards is not documented.
