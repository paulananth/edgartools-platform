# R10 Governance: a container service that holds provider credentials

Method: Snowflake documentation only; no measurements; no account touched. Claims are "from the documentation" unless marked.

## Answer

1. **Roles and privileges (from the documentation, high).** The creating role owns the service and the service runs its SQL in that role, so the owner role must hold only what the service needs ([working-with-services](https://docs.snowflake.com/en/developer-guide/snowpark-container-services/working-with-services)). Minimum: CREATE SERVICE on the schema, USAGE on the compute pool, READ on the stage ([CREATE SERVICE](https://docs.snowflake.com/en/sql-reference/sql/create-service)). ACCOUNTADMIN grants CREATE COMPUTE POOL and BIND SERVICE ENDPOINT ([privileges](https://docs.snowflake.com/en/user-guide/security-access-control-privileges)).
2. **BIND SERVICE ENDPOINT: do not grant (design, high).** It only permits public endpoints; the loader makes outbound calls only.
3. **Secrets (from the documentation, high).** Created with CREATE SECRET ([create-secret](https://docs.snowflake.com/en/sql-reference/sql/create-secret)). A container reads it as an environment variable (`envVarName`/`secretKeyRef`, not updated after creation) or as files (`directoryPath`, updated live) ([specify-secrets](https://docs.snowflake.com/en/developer-guide/snowpark-container-services/specify-secrets)).
4. **Egress (from the documentation, high).** An external access integration with `ALLOWED_NETWORK_RULES` and `ALLOWED_AUTHENTICATION_SECRETS`, attached with `EXTERNAL_ACCESS_INTEGRATIONS` ([EAI overview](https://docs.snowflake.com/en/developer-guide/external-network-access/external-network-access-overview), [working-with-services](https://docs.snowflake.com/en/developer-guide/snowpark-container-services/working-with-services)). The egress page was not retrievable (gap).
5. **Network policies (from the documentation, medium).** They govern inbound access to the account and internal stages; blocked values win; inactive until attached ([network-policies](https://docs.snowflake.com/en/user-guide/network-policies)). They do not govern a service's egress; EAI does. Best answer for key-pair logins: the service runs inside Snowflake, so the origin check matters for external clients only; the page does not state this for key-pair.
6. **Image repository (from the documentation, high) and scanning (gap).** CREATE IMAGE REPOSITORY is a schema privilege; READ lists and downloads, WRITE also pushes ([image registry](https://docs.snowflake.com/developer-guide/snowpark-container-services/working-with-registry-repository.html)). No customer-facing SPCS image scanning appears in the documentation; Snowflake scans Native App images in its own review ([Native App security](https://docs.snowflake.com/en/developer-guide/native-apps/security-na-spcs), search snippet). Best answer (medium): scan in CI before push with our own scanner.
