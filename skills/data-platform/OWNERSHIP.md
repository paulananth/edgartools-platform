# Skills: who owns what, and how they hand off

One owner for each decision and artifact; every hand-off names what travels and who receives it. the skills README (`skills/README.md`) says which skill
to open; this page says what each skill **owns, takes in, gives out and hands to**, so skills work together instead of beside each other.
A test (`tests/unit/test_skill_ownership.py`) holds the table: every skill has a row, every name exists, and a hand-off is written on both
sides (A hands off to B only if B lists A under "Receives from").

## SIPOC: a recurring load and its operation

| Suppliers | Inputs | Process (owner skill) | Outputs | Customers |
|---|---|---|---|---|
| Acquisition (completed deliveries); [data-onboarding](../data-onboarding/SKILL.md) (rules, `inputs.yaml`); the operator (the window, force publish) | Captures, rules, `rules/load-jobs.yaml`, logins, readiness facts | 1 **Gate**: readiness ([data-operations](../data-operations/SKILL.md); its AUDIT check reads [access-audit](../access-audit/SKILL.md)) | `readiness.json` or the named failing check | Every later step |
| The operator; [pipeline-orchestration](../pipeline-orchestration/SKILL.md) for a schedule | The newest loader image of `main`, the run label | 2 **Start**: `load.sh` (data-operations) | A Step Functions execution, lanes at the lane budget | [load-monitoring](../load-monitoring/SKILL.md) |
| [bookkeeping](../bookkeeping/SKILL.md), [change-journal](../change-journal/SKILL.md) | Planned work, receipts | 3 **Run**: lanes of load jobs; the journal skips what is processed | Loaded MDM, RDM and silver; run state and logs | Operator, [mdm-data-publication](../mdm-data-publication/SKILL.md) consumers |
| data-operations | Load jobs' status, processes, logs, the runtime | 4 **Watch**: load-monitoring every 30 minutes; the first look at a stall is the runtime, then the lanes against the budget | Metrics, the dashboard, a named stall | data-operations, production-support |
| load-monitoring | A stall with a lock or slow statement | 5 **Look into the store**: [database-monitoring](../database-monitoring/SKILL.md) (read-only) | Lock waiters, blockers, costly statements | production-support, data-operations |
| load-monitoring, database-monitoring, data-operations | A failure, a stall nothing explains | 6 **Diagnose**: [production-support](../production-support/SKILL.md) | Root cause with evidence, a recommendation | data-operations (recovery), [mdm-engineering](../mdm-engineering/SKILL.md) (a code fix) |
| production-support | A recommendation | 7 **Recover**: data-operations with the Bookkeeping recovery contract; restart the runtime, same run label | A finished run | The operator |
| data-operations | A finished execution | 8 **Close**: the finish, the status report, learning into skills; the catalog separately ([openmetadata](../openmetadata/SKILL.md), never inside a load) | The report with elapsed time; skill updates | The operator, [data-catalog](../data-catalog/SKILL.md) |

## Regular touch points

| When | Who looks | At what |
|---|---|---|
| Before a load | data-operations (gate), access-audit | The twelve readiness facts, one login per duty |
| Every 30 minutes during a load | load-monitoring, then data-operations | Workers running against the worker limit and the store's rows a minute, memory and CPU, failed or stalled steps, the container runtime answering |
| At a stall | load-monitoring, then database-monitoring | The runtime first, then lock waiters and costly statements |
| With every worker in use and steps waiting | load-monitoring, database-monitoring, then data-operations | Rows a minute and the database's CPU and memory at the limit; data-operations keeps, raises or lowers the `stores:` line (HOSTED-LOADS, "Balancing a load") |
| At a failure | production-support | Bookkeeping and Change Journal evidence, then the logs |
| After a load | data-operations | The elapsed time against the window, what loaded, what a skill must learn |
| On a rules change | data-onboarding or refining-rules, then openmetadata | The catalog's text, on its own, never inside a load |

## Rules of the handshake

1. **One owner.** A decision or an artifact has one owning skill; the others link to it and never restate its procedure.
2. **Both sides.** A hand-off is written by the sender (Hands off to) and the receiver (Receives from); the test fails a one-sided edge.
3. **Artifacts, not stories.** What travels is named: a status, a run label, a findings file, a recommendation with its evidence.
4. **Monitoring reads, operations acts.** load-monitoring and database-monitoring change nothing; restarts, recovery and DDL are data-operations'.
5. **Same PR.** A change to a skill's scope changes its row here in the same pull request.
