# Retained load timing reports

Use this procedure for load-time and initialization-to-entity reports. Limit report generation to **five minutes**; this is not a production load benchmark.

## Prepare the runtime before timing

Before starting the report clock, use a project environment with MDM runtime dependencies. In a fresh worktree, initialize it once with `uv sync --extra s3 --extra mdm-runtime`. `uv run --no-sync` does not install dependencies; on an empty worktree it can create an environment where the profiler fails to import SQLAlchemy. If setup is not ready, report from retained evidence and mark live profiling unavailable. Do not spend the report deadline bootstrapping dependencies.

Invoke the skill's `scripts/profile_load.py` from its directory using the prepared project environment. `steps --run` expects one Bookkeeping `pipeline_run.run_id` UUID, not the human-readable `RUN` passed to `load.sh`; it reports one Bookkeeping invocation.
For a full load's per-step intervals, resolve `RUN` and `LOGS` from the pipeline configuration and its worker environment. The loader defaults `LOGS` to `~/.local/share/edgartools/load-logs`; the pipeline may mount a different directory. Read the selected worker's retained `chain-<RUN>.log`, including its mounted host location when the worker is stopped. Repository tickets are an index to evidence, not the timing record. A missing log in one guessed directory is not evidence that timings are unavailable.

Use `load_jobs.measured` for same-day intervals: each interval runs from the first recorded attempt start to `done`, including retries and gaps between attempts. It returns minutes. Its calculation wraps at 24 hours and the log timestamps omit year and UTC offset: for longer spans, year boundaries or daylight-saving changes, require dated, timezone-qualified run evidence and calculate the elapsed seconds directly. Mark ambiguous endpoints unavailable. Concurrent lanes overlap, so their intervals do not sum to pipeline wall time. Report total wall time separately from the completed `load.sh` execution's start and finish; include readiness and finish phases when those endpoints cover them.

## Keep timings after a load

At closeout, preserve the chain state, step logs, execution start/end evidence and Bookkeeping run references in the private evidence directory before resetting a store or replacing a worker. Write a reusable JSON snapshot and a table with one row per configured step: environment and store generation, pipeline run label, step/source/target, capture references, all contributing Bookkeeping run IDs, code and Rules versions, first start, verified completion, elapsed seconds, attempt count, final state, timing basis and evidence paths. Include failed, running and unstarted steps with an explicit missing-duration reason. A running duration ends at the observation time and is provisional. Report finish and whole-pipeline wall time separately. Raw timestamps retain their timezone; display times in local ET.

Read the snapshot on later timing questions and check its run identity and observation time. Reuse retained evidence within the five-minute report budget. No complete evidence means an explicit unavailable field, never an estimate presented as a measurement.

## OpenMetadata and Grafana

Bookkeeping and retained execution records supply the timing evidence. Publish completed execution summaries to the configured OpenMetadata Pipeline after the load, through the supported catalog API with readback. Keep execution identity, status, measured start/end and evidence references associated; select fields supported by the installed server schema. The status timestamp is not an execution start time. The current `rules catalog status --bookkeeping-run` adapter publishes status and execution ID; it does not publish measured start/end or duration. Report this gap when asked for catalog timing history. Adding timing publication requires a separate implementation and schema qualification; a skill instruction alone does not provide it. The existing `load_jobs.py --catalog-status` catch-up publishes the latest run per done step, so it does not establish complete history across bundles or attempts.

Grafana shows ongoing progress, elapsed time and resource pressure from the monitoring data source, and can display history while that source retains it. Check exporter observation time, scrape health and dashboard refresh before calling a reading current. The configured monitor uses a 30-second exporter interval, a 15-second Prometheus scrape and a 10-second dashboard refresh; sampling and query time add latency. Treat it as near-real-time. Use retained execution endpoints for final durations, since a chart can miss transitions between samples. Catalog publication stays outside the load execution path.

## Five-minute workflow

1. **Scope once (first minute).** Resolve the environment and private evidence directory. Read the configured source/target inventory and dependency list once; obtain the entity-kind map from active Dataset Contracts, not source names. Check credential and hosted-qualification gates before live access. An uncleared gate means retained-only evidence, not a reason to investigate provisioning or rotate credentials. Keep every requested target in the report.
2. **Reuse, then batch (next two minutes).** Read existing measurement JSON, explicit load summaries and manifest indexes before raw logs. Reuse artifacts with their observation times and code/Rules versions. Verify only missing or stale fields through supported read-only commands. Prefer an existing batch reader; otherwise bound status and profiler calls by the remaining deadline. Retain every bundle run ID, but do not query each bundle when a retained verified snapshot covers them. Search only resolved evidence directories; read large receipt bodies or failure logs only to resolve a specific field.
3. **Calculate once (fourth minute).** Group per-run evidence by source/target and kind, preserving exact step names. Verify complete state, expected units equal verified units and zero pending deliveries. A snapshot proves its observation time, not current state; label unverified logs historical. Reconcile `considered = selected + already_processed` per invocation without adding overlapping attempts. Compute first contribution from the **earliest verified run completion**, not the minimum of each target's final completion. All-source completion requires every active contributing contract and required link target; source records are not unique masters.
4. **Write and check (by minute five).** Produce one private report and reusable structured evidence snapshot with observation time, environment label, code/Rules versions, evidence references and explicit missing-field reasons. Include each target's capture/run references, receipt digest, counts, run IDs, exact step intervals, verification state and timing basis; summarize sources and entity contributions without double-counting targets. Convert timestamps to `America/New_York` using `pytz`, never a fixed offset. Check arithmetic, inventory coverage and sensitive-content exclusion, then return the path.

At the deadline, finish from collected evidence and mark unresolved fields `unavailable` with the missing evidence and observation time. This is an evidence-complete report, not a claim that unavailable timings were measured. Do not extend discovery with recursive archive searches, historical-session consults or repeated readiness checks; further investigation is a separate task.

## Timing basis

- `active_command_seconds` requires retained `time -p` real values.
- `target_wall_seconds` requires first invocation start and final verified completion. If only Bookkeeping creation/completion times exist, call it `retained_run_span_seconds`, not target wall time.
- Step intervals are event intervals, not CPU time; their sum is not wall time.
- Initialization requires exact request and READY evidence. Missing endpoints stay unavailable; never substitute file modification times.
- Preserve raw timestamps and exact operation names. Report generation never resets, replays or starts production work for a sample.
