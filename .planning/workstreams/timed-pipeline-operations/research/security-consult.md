# Security consultation: timed pipeline operations and production support

## Recommendation

Keep the support agent advisory by default. It may inspect monitoring and retained operational evidence, correlate a run, and produce a diagnosis. It must not restart, retry, stop, alter configuration, or change infrastructure just because its diagnosis suggests doing so. Automation is limited to an operator-approved, bounded runbook action whose exact target, scope, limits, version, and rollback are checked immediately before execution. Use existing operator authorization, configuration and runbooks; do not add a separate approval registry or service. All other actions require the operator's explicit approval.

The orchestrator schedules, starts, stops, and sequences work only. Bookkeeping remains the sole owner of execution identity/state, dependencies, leases/fencing, checkpoints, retries, recovery and verified completion. The Change Journal owns immutable published change events and delivery receipts. Monitoring/orchestration must not create a competing run ledger or mark work complete. This follows the existing [Bookkeeping independence contract](../../../../skills/bookkeeping/INDEPENDENCE.md) and [Bookkeeping specification](../../../../skills/bookkeeping/SPEC.md), and the [Change Journal recovery rules](../../../../skills/change-journal/SKILL.md).

## Minimum controls

1. **Collect bounded evidence.** For each job/run, capture CPU and memory utilization/limits, task/container exit and health state, relevant log excerpts, timestamps, retries, and Bookkeeping/Journal references. Set explicit lookback, byte/row limits and deadlines. Use source references (log group/stream/event time or immutable object URI plus digest), not copied unbounded logs. Keep raw evidence in its existing owner; the report should link to it.
2. **Redact before model context and logging.** Scrub credentials, tokens, DSNs/URLs, identity data and other sensitive values before prompts, tool outputs or generated reports; avoid logging full environment/configuration. CloudWatch Logs data-protection policies can audit and mask matching sensitive data, but this is defense in depth, not a substitute for application-side minimization and redaction ([AWS CloudWatch masking](https://docs.aws.amazon.com/AmazonCloudWatch/latest/logs/mask-sensitive-log-data.html)). Restrict unmask authority.
3. **Treat logs and artifacts as hostile input.** Delimit and label them as untrusted evidence; do not follow instructions embedded in logs, job output, artifacts or tool responses. Validate every proposed tool argument and authorize it outside the model. Prompt filters alone are insufficient; OWASP recommends least privilege, parameter validation at tool boundaries, and action-specific approval for high-impact operations ([OWASP prompt-injection guidance](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html)).
4. **Split permissions by role.** Monitoring and diagnostic specialists receive read-only, narrowly scoped access to metrics/log references and control status. They cannot submit work or mutate AWS, Docker, Bookkeeping, Rules, or Journal state. For an approved action, use the existing restricted execution interface of the owning system. Do not give diagnostic experts write access, shell access, arbitrary commands, free-form resource selection, secret retrieval, or privilege escalation. Do not grant broad read access merely for convenience: logs can contain sensitive material.
5. **Check the action at execution time.** Before a bounded action, validate exact environment/account, resource/run identity, allowed state transition, runbook name and version/digest, bounds (time, retries, concurrency, resource ceiling), preconditions, and rollback/stop condition. Reject stale evidence, target mismatch, unsupported action, expired approval, or any value outside the runbook. Record who/what authorized it and the result. Human approval must show the business impact and exact action/target in readable form.
6. **Preserve evidence and ownership.** Reports contain timestamps/timezone, source references and immutable digests, observed facts versus inferences, affected run/step IDs, and whether each conclusion is verified. Never substitute an agent's summary for Bookkeeping's admitted verifier evidence or a Journal receipt. Preserve original work and fence/lease rules on recovery; no direct replay or repinning outside owner workflows.
7. **Use five whys or another explicit RCA method, then cross-check.** Distinguish symptom, trigger, root cause, contributing conditions and unknowns; stop at an evidenced cause and label hypotheses. A holistic diagnosis must consult both an architecture expert and a security expert. Neither specialist nor the support agent makes a consequential decision in isolation. Keep one consolidated report with evidence references, confidence, impact, recommended next action, and the two reviews; escalate disagreement or missing evidence to the operator.
8. **Optimize within guardrails.** Use metrics/log sampling, bounded lookbacks, existing telemetry, and the smallest diagnostic query that answers the question. Do not reduce redaction, access controls, evidence retention, approval, or verification to save cost. Do not introduce a second monitoring platform or durable orchestration store unless a measured gap requires it.

## Proposed holistic report

- Incident/run and exact environment/target.
- Impact: affected work and downstream dependencies, duration, and what is confirmed versus unknown.
- Evidence: bounded metric/log references with timestamps, immutable IDs/digests, and redaction status.
- Diagnosis: symptom → trigger → root cause (five-whys chain or named alternative), contributors, confidence, and falsifying evidence sought.
- Architecture review: Bookkeeping/Journal ownership respected; dependency, lease/fencing, idempotency and recovery implications.
- Security review: trust boundaries, sensitive-data exposure, permissions, prompt-injection/tool misuse risks, and action authorization.
- Recommendation: no action, operator decision required, or exact preapproved runbook action with version, target, bounds, preconditions and rollback.
- Execution record, if authorized: approver, runbook version, executor identity, validated target, outcome, and retained evidence references.

## Conflicts and unknowns

- The requested portable AWS+Docker contract is not established by this advisory. The repository guide explicitly scopes active deployment to AWS; Docker is used for local/shared test stores, while cloud/container monitoring APIs, metrics names and deployment adapters remain unspecified. Treat AWS and Docker as replaceable adapters behind a common job/run observation and action contract; do not claim Docker production support until its runtime/authority model is defined.
- Existing Bookkeeping recovery is owner-controlled and bounded. A proposed orchestrator stop/retry action must map to a supported Bookkeeping transition; no direct state mutation or competing retry counter is acceptable.
- The repository's existing contracts establish roles, fencing and evidence boundaries for Bookkeeping tasks, but do not define the support-agent IAM roles, log retention/TTL, masking policy, approver identity mechanism, or approved runbook registry. These are implementation details to resolve against existing policy/configuration before production use; do not introduce a new registry or service to represent approvals.
- CPU/memory/log visibility and query costs depend on the deployed AWS/Docker telemetry configuration; no live inspection or deployment was performed, so availability and cost are unverified.
