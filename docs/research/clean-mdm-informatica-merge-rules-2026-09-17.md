# Informatica merge rules: evidence for Clean MDM

Research date: 2026-09-17. Status: research, not an accepted design decision. Only first-party Informatica sources support the findings below. Product versions are explicit because Multidomain MDM Hub and MDM SaaS do not have one interchangeable contract. No vendor runtime was tested.

## Findings

| Design question | Documented behavior | Consequence for Clean MDM |
| --- | --- | --- |
| Is matching the same operation as consolidation? | Multidomain MDM 10.5 HF4 `SearchMatch` returns candidate records, match-rule details, and an automatic-merge indicator. A client can use the candidates with Merge, MultiMerge, or Link. [SIF guide, SearchMatch, p. 133](https://docs.informatica.com/content/dam/source/GUID-8/GUID-8A16DD83-1E2C-4CA2-818F-05A6A2EEE8B9/22/en/MDM_105HF4_ServicesIntegrationFrameworkGuide_en.pdf). | Record an identity-match decision separately from field selection and publication. A possible match need not change a master. |
| Must automatic merging require an exact authoritative ID? | Multidomain MDM 10.5 HF4 supports exact-only base objects and fuzzy base objects containing fuzzy, exact, or combined match columns. [Match types](https://docs.informatica.com/master-data-management/multidomain-mdm/10-5-hotfix-4/configuration-guide/part-4--configuring-the-data-flow/mdm-hub-processes/match-process/exact-match-and-fuzzy-match-base-objects.html). Separately, Informatica's MDM SaaS best-practices presentation shows automated fuzzy rules using strongly similar name, address, and exact birth date. [SaaS best practices, slide 21](https://www.informatica.com/content/dam/informatica-cxp/techtuesdays-slides-pdf/MDM%20SaaS%20Match%20and%20Merge%20Best%20Practices.pdf). | Exact-ID-only automation is an optional release policy. It is not a universal vendor rule. Fuzzy automatic matching needs measured precision and explicit conflicting-identifier checks. |
| How does manual review enter? | Multidomain MDM 10.4 HF1 describes manual rules as sufficient similarity for steward attention but insufficient similarity for automatic merging. [Manual merge](https://docs.informatica.com/master-data-management/multidomain-mdm/10-4-hotfix-1/data-steward-guide/appendix-a--glossary/glossary-of-terms/manual-merge.html). MDM SaaS has automatic, manual, and threshold-based strategies in its first-party best-practices examples. [SaaS best practices, slide 21](https://www.informatica.com/content/dam/informatica-cxp/techtuesdays-slides-pdf/MDM%20SaaS%20Match%20and%20Merge%20Best%20Practices.pdf). | Define automatic, review, and non-match outcomes. The previous 0.85/0.80 proposals have no validation from these documents. |
| Does every record get compared? | The MDM SaaS online help documents candidate generation first, followed by declarative rules applied only to candidates. Narrow searches can miss matches. The online-help page is a rolling `prod` URL with a 2020–2021 copyright footer, not a pinned release. [Candidate selection](https://onlinehelp.informatica.com/IICS/prod/mdmconfig/en/ff-b360-configure-match/Candidate_selection_criteria.html). | Measure candidate recall separately from match accuracy. A good scoring rule cannot recover a pair excluded by candidate generation. |
| Does the smallest identity ID always survive? | Multidomain MDM 10.4 batch merging preserves a consolidated ID when matched against a new record. Lowest ID wins when both records are new. Merge SIF and real-time Data Director merging preserve the chosen target ID. [ROWID_OBJECT survivorship](https://docs.informatica.com/master-data-management/multidomain-mdm/10-4/configuration-guide/part-4--configuring-the-data-flow/mdm-hub-processes/about-informatica-mdm-hub-processes/rowid_object-survivorship.html). | Replace the earlier blanket smallest-ID recommendation with an explicit decision about established identities. These rules do not establish what every path does when two consolidated identities collide. |
| Are source IDs retained separately? | Multidomain MDM 10.5 HF2 stores generated `ROWID_OBJECT` on the base object; source primary key `PKEY_SRC_OBJECT` and source-system identity are retained in its cross-reference table. [Load inserts](https://docs.informatica.com/master-data-management/multidomain-mdm/10-5-hotfix-2/configuration-guide/part-4--configuring-the-data-flow/mdm-hub-processes/load-process/run-time-execution-flow-of-the-load-process/load-inserts-and-target-base-objects.html). | Keep source-record identity separate from master identity. This evidence alone does not prove that all retired master IDs remain API aliases forever. |
| How are field winners selected? | Multidomain MDM 10.5 HF4 configures trust by column and source, considers quality and age, permits decay, and permits steward overrides. Highest trust wins. [Trust settings](https://docs.informatica.com/master-data-management/multidomain-mdm/10-5-hotfix-4/configuration-guide/part-4--configuring-the-data-flow/mdm-hub-processes/load-process/trust-settings-and-validation-rules/trust-settings.html). | A field policy can depend on source, quality, and effective time. Identity confidence must not substitute for field authority. This source does not establish atomic selection of a complete address or other field group. |
| Can null erase a value? | The Multidomain MDM 10.3 release guide describes the change introduced in 10.1 HF2: `Allow Null Update` can permit null to reach the base object; disabling it downgrades trust for null. [Release guide, Allow Null Update](https://docs.informatica.com/content/dam/source/GUID-9/GUID-975A506E-8126-4185-8858-4375A303C0D4/27/en/MDM_103_ReleaseGuide_en.pdf). | Null behavior is a policy choice. Define missing, unknown, explicit clear, and source withdrawal separately. The legacy rule is not proof of current SaaS behavior. |
| Does deleting one contribution delete the master? | Multidomain MDM 10.5 HF2 says base-object values reflect active cross-reference records; active values take precedence over pending or deleted ones. [Record states and survivorship](https://docs.informatica.com/master-data-management/multidomain-mdm/10-5-hotfix-2/configuration-guide/part-3--building-the-data-model/state-management-and-bpm-workflow-tools/state-management-in-the-mdm-hub/record-states-and-base-object-record-value-survivorship.html). | Distinguish withdrawal of one source assertion from retirement of the identity. |
| What does unmerge reverse? | Multidomain MDM 10.4 SIF distinguishes linear from tree unmerge. Given 3 merged into 2, then 2 into 1, linear unmerge of 2 restores 2 alone; tree unmerge restores 2 with 3. Field values are recalculated. Cascade unmerge of affected children is separately configurable. [SIF guide, Unmerge, p. 140](https://docs.informatica.com/content/dam/source/GUID-8/GUID-8A16DD83-1E2C-4CA2-818F-05A6A2EEE8B9/18-1-1/en/MDM_104_ServicesIntegrationFrameworkGuide_en.pdf). | Specify the resulting identity partition, child relationships, and field recomputation. “Reverse the merge” is not a complete procedure. |

## Limits that remain explicit

The reviewed sources do not establish a general authoritative-ID conflict veto, persistent cannot-link rule after unmerge, atomic survivorship for related fields, or a universal policy for two established master identities. These are open Clean MDM design questions, not evidence of absent Informatica capabilities.

A legacy 10.1 HF3 steward guide says unmerge reconstructs from the **current** cross-reference contribution and reinstates its original ID. It also warns that user-defined foreign keys remain attached to the remaining merged object. This is useful evidence that source updates and relationship reassignment need separate treatment; it is not a guarantee for every modern Informatica deployment. [Data Steward Guide, Effects of Unmerging a Row, p. 50](https://docs.informatica.com/content/dam/source/GUID-6/GUID-671C5A40-BDC0-40DE-A0D0-256E9162966D/10-1-1/en/MDM_101HF3_DataStewardGuide_en.pdf).

Several official HTML pages returned HTTP 403/503 during this research. Findings use accessible first-party pages, PDFs, and indexed first-party excerpts. Older releases are labeled; their behavior must not be silently applied to MDM SaaS.

## Interview decisions suggested by this evidence

These are proposed questions, not accepted rules:

1. An incoming Company record matches two established Company identities. May it combine them automatically, or must a steward decide? Treat this separately from attaching one source record to one identity.
2. If two established identities are confirmed duplicates, which published ID survives, and what must a lookup of the retired ID return?
3. If exact authoritative identifiers are missing, what evidence may permit an automatic match? Set a measured false-merge limit before choosing score cutoffs.
4. Which related fields must come from one source assertion, such as an address with its country and postal code?
5. After an incorrect merge, where do later source corrections, steward edits, and relationships belong? Must the rejection prevent the same automatic match from recurring?
