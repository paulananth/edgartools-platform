# DataKitchen TestGen test types and fit to three silver tables (2026-11-02)

Primary source: `github.com/DataKitchen/dataops-testgen` (Apache-2.0), release tag `5.134.0`,
commit `3606859cf8bb4f809d2b19acc51462420829c4ab` (latest release at fetch; `main` pushed 2026-10-21).
All test types live as one YAML file each in `testgen/template/dbsetup_test_types/test_types_<Name>.yaml`
at that tag (89 files). Other DataKitchen repos (`dataops-observability`, `DKUtils`, etc.) were listed but not read; only `dataops-testgen` defines data quality test types.
No request went to any provider; only GitHub was read. Invented examples only, no data values.

## How a TestGen test type is defined (from the YAML files)

Each file has a `test_types:` block with: `test_type` (id), `test_name_short/long`, `test_description`,
`usage_notes`, `measure_uom`, `default_parm_columns` (comma list of parameter names), `default_parm_prompts/help/required`,
`default_severity` (`Fail`: 74 types, `Warning`: 14, `Log`: 1 `Table_Freshness`), `run_type`
(`CAT` 69 = aggregate SQL measure compared to a threshold, `QUERY` 16 = standalone SQL, `METADATA` 4),
`test_scope` (column 67, table 11, referential 8, custom 2, tablegroup 1), `dq_dimension`
(Validity 23, Consistency 39, Completeness 9, Accuracy 8, Timeliness 4, Uniqueness 3, Recency 2),
`threshold_description`, and per SQL flavor a `cat_test_conditions` entry (`measure` SQL, `test_operator`, `test_condition`)
and `target_data_lookups` (SQL that lists the failing values). Snowflake is a supported flavor.
Threshold model: a CAT test computes one measure per column and fails when `measure <operator> threshold`
(for most counting tests the operator is `>` and the default threshold is a count of tolerated bad records, typically 0;
the per-type default value lives in `default_parm_values`, which I did not tabulate). Severity is a per-type default
(`default_severity`); I did not verify where a per-test override is stored.
Many types are "baseline" types: their parameters are filled from a profiling run (frequent values, min, max, mean, sd), a workflow this platform does not use.
Files: e.g. `.../test_types_LOV_Match.yaml` (measure `SUM(CASE WHEN NULLIF(col,'') NOT IN {BASELINE_VALUE} THEN 1 ELSE 0 END)`, operator `>`, nulls and empty strings pass);
`.../test_types_Dupe_Rows.yaml` (query `GROUP BY {GROUPBY_NAMES} HAVING COUNT(*) > 1`, threshold `skip_errors`);
`.../test_types_Condition_Flag.yaml` (`SUM(CASE WHEN {CUSTOM_QUERY} THEN 1 ELSE 0 END)`, expression true = failing row, threshold = tolerated failing rows).

## 2. Mapping to the engine's three kinds

The engine kinds: `identifier` (registered shape plus check digit), `in_set` (value in allowed list), `one_value` (within a group, one value; minority flagged).

| Engine kind | TestGen types that map | Notes |
|---|---|---|
| `in_set` | `LOV_Match` (list from baseline, nulls and empty strings pass), `Constant` (a one-element list), `Valid_Month` (inactive), `US_State` (fixed list of codes), `Required_No_Placeholder` (the inverse: placeholder list must not appear, plus not null) | `LOV_All` also needs every listed value to be present (a completeness side, new). Parameter is a literal list `('A','B')` plus a tolerated failing-row count. |
| `identifier` | none | No type in the 89 files checks a check digit or a registered identifier shape. A word search for luhn/cusip/isin/checksum/check digit found only a code comment in `Dupe_Rows`. The closest is `Pattern_Match` (regex only, no check digit) and `Valid_US_Zip`, `Email_Format` (fixed regexes). |
| `one_value` | none directly | TestGen has no "within a group, one value, flag the minority" type. `Constant` is one value for the whole column, fixed from a baseline. `Aggregate_Balance*`, `Combo_Match` and `CUSTOM` compare to a reference table. The group-consistency check would be `CUSTOM` or `Condition_Flag` SQL. |
| New kind needed: uniqueness | `Unique`, `Dupe_Rows` | Composite key uniqueness, threshold 0. |
| New kind needed: not null | `Required` | |
| New kind needed: range / bound | `Min_Val`, `Max_Val`, `Min_Date`, `Max_Date`, `Future_Date`, `Future_Date_1Y`, `Text_Length_Range`, `Alpha_Trunc` | |
| New kind needed: row condition | `Condition_Flag`, `CUSTOM`, `SQL_Metric`, `Metric_Trend` | Free SQL; the engine would need a restricted expression form. |
| New kind needed: pattern | `Pattern_Match`, `Email_Format`, `Street_Addr_Pattern`, `Valid_US_Zip`, `Valid_US_Zip3`, `Valid_Characters` | |
| New kind needed: referential | `Combo_Match`, `Aggregate_Balance`, `Aggregate_Balance_Percent`, `Aggregate_Balance_Range`, `Aggregate_Minimum`, `Timeframe_Combo_Match`, `Timeframe_Combo_Gain`, `Distribution_Shift` | Needs a second table. |
| New kind needed: volume / freshness / schema | `Row_Ct`, `Row_Ct_Pct`, `Volume_Trend`, `Recency`, `Freshness_Trend`, `Table_Freshness`, `Daily/Weekly/Monthly_Rec_Ct`, `Match_Column_Ct`, `Match_Column_Type`, `Schema_Drift`, `Schema_Conformance` | Table level, history based. |
| Statistical / baseline drift (out of scope for a first set) | `Avg_Shift`, `Incr_Avg_Shift`, `Variability_*`, `Outlier_Pct_*`, `Missing_Pct`, `Unique_Pct`, `Distinct_Value_Ct`, `Distinct_Date_Ct`, all `Match_*` baseline types, `Dec_Trunc` | Compare to a profiled baseline; noisy for filed facts that grow every quarter. |

| 5 | company_fact (also line_item, measure) | the key columns, e.g. company_key, concept, accession, filed | `Required` | NEW: not null | tolerated 0 | Key columns that are null defeat check 1 (many engines treat nulls as distinct). |

Checks that run today: 4 and 9 (and `Constant` as a one-element `in_set` where a column should be fixed).
Checks 1 to 3, 5 to 8 need new kinds: unique key (1-3), not null (5), row condition (6-7), bound (8).
Not recommended first: baseline/statistical types, `Match_*` types, `Volume_Trend`/`Row_Ct` (useful later for snapshot size per run, new volume kind), `Combo_Match` for line_item accession present in company_fact (needs a referential kind).

Currency, unit and taxonomy are natural `in_set` columns, but I did not have their registered lists, so I give no values; an ISO currency column is more naturally an `identifier`-style registered shape if the engine registers one.
