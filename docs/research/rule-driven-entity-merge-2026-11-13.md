# Can one Merge Stage serve Company, Person, and Security?

**Code snapshot:** `9b00663adb4dc859be5ac21be31b75248e2fb9cd` (current `origin/main` in the research worktree, 2026-11-13). This note reads repository code and committed rules only; it does not claim a live source run or activation.

## Finding

Yes: a shared Merge Stage can accept one prepared source assertion at a time for Company, Person, or Security. The current design already groups each input batch by `record["kind"]` and calls the same `merge_file` function with kind-specific settings ([`workers/mastering_merge.py:90-100`](../../edgar_warehouse/workers/mastering_merge.py#L90)). A one-row input is not a one-row golden master: the merge retrieves prior bindings, candidate identifier holders, peer assertions and stored history before deciding how that assertion changes a master ([`mastering/merge.py:211-243`](../../edgar_warehouse/mastering/merge.py#L211), [`mastering/merge.py:260-288`](../../edgar_warehouse/mastering/merge.py#L260)).

A row by itself does not say whether two source rows are the same entity. Cross-source mastering still depends on the row's identifiers and matching rules. A row with no usable matching evidence may wait, be reviewed, or be created according to the applicable policy. The source row is therefore a suitable common input unit, while identity decisions remain governed by configured evidence and policy.

## What is configured and shared

- `mdm.prepare` is a generic adapter from a named reading table to bounded records files. It optionally unwraps an object-valued `record_column`, can carry selected row extras, deduplicates on configured columns, and pins source dataset, policy, consumer, publication and `as_of` in the manifest ([`workers/mdm_prepare.py:3-39`](../../edgar_warehouse/workers/mdm_prepare.py#L3), [`workers/mdm_prepare.py:107-152`](../../edgar_warehouse/workers/mdm_prepare.py#L107)). It does not branch on Company, Person, or Security.
- The normal merge worker retrieves the registered policy using the manifest digest and passes each kind's records to the same merge module ([`workers/mastering_merge.py:56-65`](../../edgar_warehouse/workers/mastering_merge.py#L56), [`workers/mastering_merge.py:90-100`](../../edgar_warehouse/workers/mastering_merge.py#L90)).
- Identity matching reads configured identifier contracts and matching rules. The engine filters rules for `settings.kind`; holder candidates are explicitly constrained to masters of the same kind ([`mastering/merge.py:246-248`](../../edgar_warehouse/mastering/merge.py#L246), [`mastering/merge.py:260-288`](../../edgar_warehouse/mastering/merge.py#L260)).
- Field and profile survivorship is sent to the common Rust `prepare_master_records` function with the kind, claims, policy, overrides, and configured profile eligibility. Rust builds the master from those inputs ([`mastering/merge.py:453-469`](../../edgar_warehouse/mastering/merge.py#L453), [`crates/source-contract/src/master_records.rs:144-159`](../../crates/source-contract/src/master_records.rs#L144), [`crates/source-contract/src/master_records.rs:245-280`](../../crates/source-contract/src/master_records.rs#L245)).
- The repository has separate policy data for Company, Person, and Security, for example [`rules/merge/kinds/company.yaml`](../../rules/merge/kinds/company.yaml), [`rules/merge/kinds/person.yaml`](../../rules/merge/kinds/person.yaml), and [`rules/merge/kinds/security.yaml`](../../rules/merge/kinds/security.yaml). Those files state source priority, rules, and identifier contracts instead of requiring a separate merge implementation for each entity.

## What remains code-defined

The Merge Stage is not a no-code rule interpreter. Python and Rust implement the stable operations and constraints: batch and transaction boundaries, idempotency, same-kind joins, conflict checks, waiting/release, review records, aliasing and reversal, temporal folding, and applying rule families. For example, `_merge` runs identifier matching, configured name matching, exact-name matching, waiting/review handling, then master projection in a fixed order ([`mastering/merge.py:211-243`](../../edgar_warehouse/mastering/merge.py#L211)). Some behavior is also concretely specialized in code: the name-pair path reads a `cascade.lei`, persists the LEI as a name lookup key, and checks held LEIs ([`mastering/merge.py:61-67`](../../edgar_warehouse/mastering/merge.py#L61), [`mastering/merge.py:351-387`](../../edgar_warehouse/mastering/merge.py#L351)). Thus the shared pipeline is generic across kinds, but every part of matching is not declarative. Policy controls which configured rules and contracts apply and their values; code supplies the family semantics and some dedicated workflows.

There are also code-level fields and record concepts (assertion identity, `kind`, identifiers, fields, profiles, relationships) that each source rule must map into. The assertion constructor validates the supported kind and normalizes these common fields ([`mdm/evidence.py:27-44`](../../edgar_warehouse/mdm/evidence.py#L27), [`mdm/evidence.py:71-97`](../../edgar_warehouse/mdm/evidence.py#L71)). If a new entity behavior cannot be expressed by existing rule families, contracts, or catalog data, it needs a shared engine capability before a rule can use it.

So the precise answer to “is merge hard coded?” is: **the merge algorithm and its supported operations are implemented in code; entity/source choices and policy values are configured.** It is not a separate hard-coded Company/Person/Security merge implementation, and it is not arbitrary behavior that can be expressed entirely in YAML.

## Boundary and recommendation

Keep one Merge Stage over a common assertion shape. Treat each source rule's job as producing that shape (including the configured entity kind and evidence), and use the kind's versioned policy for identity, field/profile survivorship, and other supported behavior. Keep transaction safety and generic rule interpretation in the shared engine. Add a new rule family or shared primitive only when a required behavior cannot be represented by current configuration; avoid per-entity merge forks.

Committed storage-adapter tests exercise the same entry point with Company and Security records, and exercise Person and Fund under their real rules with repeat-pass assertions ([`tests/storage_adapters/test_mastering.py:90-123`](../../tests/storage_adapters/test_mastering.py#L90), [`tests/storage_adapters/test_mastering.py:354-376`](../../tests/storage_adapters/test_mastering.py#L354)); Company name-pair arrival order is also covered ([`tests/storage_adapters/test_mastering.py:421-445`](../../tests/storage_adapters/test_mastering.py#L421)). This is code-level test evidence, not a claim those tests were executed for this research. The recorded history supports the shared path: recent changes add Security matching behavior and Company name-pair integration in the same `mastering/merge.py`, rather than introducing entity-specific merge modules ([`git log --follow edgar_warehouse/mastering/merge.py`, snapshot at `9b00663a`](../../edgar_warehouse/mastering/merge.py)). That history and tests do not prove every source has equivalent end-to-end qualification. This research did not run the installed caller matrix or execute source loads.
